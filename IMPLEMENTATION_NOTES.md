# Implementation Notes

This document records the substrate and architectural decisions made during
implementation.

---

## Chosen Extraction Substrate: Hand-Walking the AST

### What the binary actually does

The python-language parser (Passes 1, 2, and 3 in `internal/parser/python/parser.go`) uses
**hand-walking** to traverse the gotreesitter parse tree:

- `gotreesitter.Walk(root, fn)` — a depth-first recursive walk that calls `fn` for
  every node in the tree.
- `node.ChildByFieldName("name", lang)` — retrieves a specific named child field
  by field name rather than by numeric index position.

Each extraction concern (symbol discovery, call collection, import map building) is
its own recursive visitor function organized as a stateful visitor over the tree.

### What typed-query codegen would look like (and why it was not used for codeweaver v1)

Tree-sitter supports a **query language** (`.scm` files using a Lisp-like syntax)
that lets you describe patterns declaratively:

```scheme
(function_definition
  name: (identifier) @fn_name)
```

This is analogous to writing a SQL `SELECT` statement against a database rather
than manually iterating every row with a pointer. The query engine compiles the
pattern into an efficient tree traversal, yielding typed match structs
(`FunctionDefinitionMatch`, etc.) with direct `Node` pointers — no string
switching on node types required.

**Real-life analogy:** Queries are like telling a librarian "bring me every book with
'Python' in the title." Hand-walking is like personally checking every shelf yourself.
Both find the same books; the librarian is faster for complex searches, but you
personally know the shelf order and can validate your own counting as you go.

### Why hand-walking was chosen for codeweaver v1

1. **Parity gate validates correctness directly.** The hand-walking traversal order
   matches the committed snapshot fixture baselines 1:1. The snapshot fixture
   tests in `internal/parser/python/parser_test.go` confirm byte-level agreement
   between the Go binary's output and the committed `*.expected.json` baselines.
   Introducing a query layer adds an indirection that the parity gate cannot see
   through as transparently.

2. **tsquery MatchPattern naming-collision issue.** When multiple `.scm` files in
   the same Go package are compiled via `cmd/tsquery`, the generated `MatchPattern`
   function names collide if two patterns share a capture name (e.g., both
   `extract_symbols.scm` and `extract_calls.scm` use captures named `@fn_name`).
   The collision produces a compile error. The fix (namespacing captures per file)
   requires either a code-generation wrapper or a naming convention enforced by
   convention — both add friction that is unjustified when the simpler hand-walking
   approach already passes the parity gate.

3. **No `cmd/tsquery` generator exists in this binary.** Any `*_query.go` files with
   "Code generated by tsquery; DO NOT EDIT" headers would be misleading — no
   `cmd/tsquery` command has been implemented. The extraction logic lives entirely in
   the hand-walking visitor functions in each language's `parser.go`. Shipping
   infrastructure whose source of truth is a fictitious generator is misleading and
   creates false confidence in regenerability.

### Consequences of the hand-walking choice

- **The parser is the single source of truth for extraction logic.** There are no
  `.scm` files documenting "what we extract" in a declarative form. If a new
  extraction concern is added (e.g., decorators, type annotations), the change lives
  entirely in `parser.go`. Code reviewers and future agents must read `parser.go`
  to understand what is extracted.

- **Both Python and TypeScript parsers use hand-walking for consistency.** When
  the TypeScript parser was added, it followed the same pattern — using a query-based
  approach for TypeScript while Python uses hand-walking would create an inconsistent
  substrate. Both parsers use `gotreesitter.Walk` + `node.ChildByFieldName`.

- **Query-based extraction may be revisited when warranted.** If profiling shows that
  hand-walking is an allocation bottleneck (unlikely — the overhead is small), or if a
  new extraction concern is genuinely easier to express as a query, the decision can be
  revisited. The fitness function: implement the query-based variant as a benchmark
  alongside the hand-walking baseline and compare `testing.B` throughput numbers. Only
  switch if the query-based variant is ≥10% faster AND the MatchPattern naming-collision
  issue is resolved upstream.

## TypeScript Parser Substrate

The TypeScript parser follows the same substrate as the python-language parser:

- `gotreesitter.Walk(root, fn)` for traversal.
- `node.ChildByFieldName("field_name", lang)` for named field access.
- One visitor function per extraction concern (symbols, calls, imports).
- A `FileResult`-equivalent struct that integrates with `parser.ResolveMultiFile`.

If typed queries are adopted in a future change, the change covers both the python and
TypeScript parsers together under a single ADR-level decision — not language by language.

The TypeScript parser in `internal/parser/typescript/parser.go`
uses `gotreesitter.Walk` only in `findFirstErrorByte` (error detection), and direct
child iteration via `node.Children()` + `node.ChildByFieldName` for the symbol and
call extraction passes. The pattern is identical across languages: a stateful
recursive visitor (`visitSymbols`) for Pass 1 and a second stateful recursive visitor
(`visitEdges`) for Pass 2. No `.scm` files were introduced.

Grammar selection is handled by `selectGrammar(relPath)`:
- `.tsx` → `grammars.TsxLanguage()` (grammar name: `"tsx"`)
- `.ts`, `.mts` → `grammars.TypescriptLanguage()` (grammar name: `"typescript"`)

Both grammars are lazily initialized via `sync.Once`: grammars are not loaded at startup;
each grammar is initialized only when first needed for that language.

The `this.method()` resolution for TypeScript was handled by extending the shared
`resolveRawCall` function in `types.go` to recognize `"this"` as an intra-class
receiver alongside `"self"` and `"cls"` (the python-language equivalents). This keeps
the resolution logic in one place so both parsers share the same resolution path.

## `parse_errors` Field

The `parse_errors[]` field is populated when `tree.RootNode().HasError()` is true:
a `ParseError` entry with `error_code: "E_PARSE_INCOMPLETE"` and the byte offset of
the first error node is appended. Surfacing parse errors explicitly via `parse_errors`
is an intentional design choice: partial results for a syntactically broken file are
still emitted alongside the error entry rather than silencing the whole file.

This population is within the v1.0 envelope's documented forward-compatibility:
the field is `omitempty` so it is absent for files without errors, and API consumers
use Pydantic v2's default `extra="ignore"` to tolerate new fields gracefully.
No `schema_version` bump is required.

## Two-Tier Language Dispatch

Language dispatch in the codeweaver binary is a two-tier strategy.

**Tier 1 — Language package selection** (`internal/parser/dispatch.go::DetectLanguage`):
Selects which language package handles the file based on the lowercased file extension.
For example, `.py` → the `python` package; `.ts`, `.tsx`, `.mts` → the `typescript` package.
This is the shared dispatch layer: adding a new language (e.g., Go, Rust) adds one case
here. No existing language's tier-2 logic is modified.

**Tier 2 — Grammar variant selection** (per-language `selectGrammar` in each package):
Within a language package, selects the grammar variant. For TypeScript this is the
key step: `.tsx` files require `grammars.TsxLanguage()` (which understands JSX angle
brackets), while `.ts` and `.mts` use `grammars.TypescriptLanguage()`. Python currently
has only one grammar and does not implement a meaningful tier-2 selector, but the
architecture is symmetric.

**Rationale:** Per-language quirks (the TSX vs TypeScript JSX disambiguation, any future
Python `.pyi` stub handling, etc.) belong inside the language package, not in the shared
dispatch layer. Keeping tier-2 logic in the language package means a new language never
touches `dispatch.go`, and `dispatch.go` never needs to know about `.tsx` vs `.ts`.

**Adding a new language:**
1. Add a Tier-1 case in `internal/parser/dispatch.go::DetectLanguage`.
2. Create `internal/parser/<language>/parser.go` with a `ParseFile` function and an
   internal `selectGrammar` (or equivalent) for grammar-variant selection. Export a
   `GrammarVersion() string` function returning `"gotreesitter-vX.Y.Z/<grammar-name>"`.
3. Wire into `internal/cli/parse.go` dispatch switch — no changes to `resolve.go`.
4. Wire into `internal/cli/version.go` `Grammars` map:
   `grammars["<language>"] = <language>.GrammarVersion()`
   Both `parse.go` and `version.go` import language packages; missing either touchpoint
   means `codeweaver version --json` will not report the new grammar, which breaks
   diagnostic correlation when consumers see output from that language.

## No Runtime Network Calls

The "no network calls from the binary" rule means no runtime network calls at the
binary's call boundary. Verified via: the closure contains no invocations of
`net.Dial`, `net.Listen`, `net.Resolver.LookupHost`, or equivalent.

Transitive imports of the `net` package via `cobra → pflag → net` (for IP-flag
type support) and `text/template → net/url` (HTML-escaping helpers) are accepted.
These symbols are linked into the binary but are unreachable at runtime because:
(a) codeweaver registers no IP-typed flags, and (b) codeweaver uses no HTML
templates. The enforcement layer is:

- `scripts/check-stdout-invariant.sh` (checks stdout purity — no log lines, no ANSI)
- `govulncheck` (run by build-engineer on every dependency bump)

Any future dependency that introduces a reachable network path violates the
no-outbound-network invariant and must be caught at the dependency-proposal
stage, not post-merge.
